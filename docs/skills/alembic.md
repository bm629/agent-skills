# alembic

> Run **Alembic schema migrations** on top of a SQLAlchemy 2.x data layer that
> targets **SQLite, PostgreSQL, and MySQL** from one migration history. Wires
> `env.py` / `alembic.ini` to your models' `Base.metadata` (DB URL from the
> environment, sync-first with a short async `run_async_migrations` note), runs
> the full **revision → autogenerate → review → upgrade/downgrade** workflow and
> branch resolution (`history` / `current` / `heads` / `merge`), and owns the two
> load-bearing pieces: **autogenerate drafts, you review** (its blind spots cause
> silent data loss), and the **SQLite batch / move-and-copy** gotcha (SQLite can't
> `ALTER` most schema, so write alters in `batch_alter_table` style — the same
> code emits plain `ALTER` on PG/MySQL). Also owns the **`create_all()` vs Alembic**
> decision and the **baseline-stamp** adoption path. Not SQLAlchemy model/engine
> authoring (`sqlalchemy`), not the job-queue loop (`sql-job-queue`).

## Purpose

Alembic gives a shipped schema a version history; doing that across three dialects
from one set of revision files needs two disciplines a tutorial usually skips.
This skill wires Alembic to an existing `Base.metadata` (the `sqlalchemy` sibling
owns the models), sources the DB URL from the environment so one history runs on
SQLite locally and PG/MySQL elsewhere, and enforces the load-bearing rules:
**autogenerate is a draft generator, not a source of truth** — it sees a rename as
drop+add (data loss), misses most `server_default` and `CHECK`/named-constraint
changes, and is blind to un-imported models — so you review every generated file;
and **SQLite can't `ALTER` most schema**, so every alter is written in
`batch_alter_table` (move-and-copy) style, which recreates the table on SQLite while
emitting ordinary `ALTER` on PG/MySQL. It also owns the `create_all()`-vs-Alembic
decision and the `alembic stamp head` baseline path for adopting Alembic on a
`create_all`'d database.

## When to activate

- ✅ Wiring Alembic (`env.py` + `alembic.ini`) to an existing `Base.metadata` so autogenerate can diff live schema against your models.
- ✅ Authoring a migration — empty (`revision`) or drafted (`revision --autogenerate`) — and reviewing/editing it before applying.
- ✅ Running `upgrade`/`downgrade`, inspecting `history`/`current`/`heads`, or resolving multiple heads with `merge`.
- ✅ Writing ONE migration that must apply on SQLite, PostgreSQL, and MySQL — reaching for batch (move-and-copy) operations.
- ✅ Deciding `create_all()` vs Alembic, or stamping a baseline to adopt Alembic on a `create_all`'d DB.

### When NOT to activate

- **Defining SQLAlchemy models / `Engine` / URLs / sessions** → `sqlalchemy` (this skill only wires Alembic to a `Base.metadata` that already exists).
- **Building a job queue / scheduler / lease loop** on the migrated schema → `sql-job-queue`.
- **Raw SQL DDL with no version history** — if you genuinely don't need history, see the `create_all()` decision.

## Workflow

| Step | Does |
|---|---|
| 1 Init | `alembic init alembic` scaffolds `alembic.ini` + `alembic/` (`env.py`, `script.py.mako`, `versions/`). |
| 2 URL from env | Don't commit a real URL; `config.set_main_option("sqlalchemy.url", os.environ["DB_URL"])` — one history, many dialects. |
| 3 `target_metadata` | `target_metadata = Base.metadata` and **import the models** so every table is visible to autogenerate. |
| 4 Online runner | `render_as_batch=True` (SQLite), `compare_type` / `compare_server_default`, a `naming_convention`, `NullPool`. |
| 5 Author | `revision` (empty) or `revision --autogenerate` (drafts) — then **review and edit** before applying. |
| 6 Apply/inspect | `upgrade head` / `downgrade -1` / `current` / `history` / `heads`. |
| 7 Multi-dialect batch | `op.batch_alter_table(...)` — move-and-copy on SQLite, plain `ALTER` on PG/MySQL, from one script. |
| 8 Branching | `alembic merge` to resolve multiple heads (records both parents). |
| 9 Async note | Point at a sync URL, or `run_async_migrations` with `run_sync(do_run_migrations)` via the greenlet bridge. |

## Hard rules it enforces

- **Autogenerate drafts; you review and edit every script before applying** — never `upgrade` an unreviewed autogenerated revision (renames and constraint changes silently lose data).
- **Write migrations in batch style when SQLite is a target** — `render_as_batch=True` + `op.batch_alter_table(...)`; the same code stays correct on PG/MySQL.
- **Set `target_metadata = Base.metadata` and import the models** — an un-imported table is invisible to autogenerate.
- **Source the DB URL from the environment** — not a committed `alembic.ini` literal.
- **Every `upgrade()` has a true-inverse `downgrade()`** — no `pass` downgrades.
- **Use a `naming_convention`** so the SQLite batch move-and-copy can reference and preserve named constraints.

## `create_all()` vs Alembic — the decision (this skill owns it)

`Base.metadata.create_all()` is the right call only for greenfield/not-yet-shipped
schemas, throwaway DBs, and test/dev bootstrap (where the `sqlalchemy` sibling uses
it) — it has **no version history, no incremental change, no downgrade**. Reach for
Alembic the moment the schema is **shipped, runs in multiple environments, or
evolves over time**. To adopt Alembic on a `create_all`'d DB: author a **baseline**
migration whose `upgrade()` creates the current schema, then run `alembic stamp head`
on the existing DB to record it as already-applied **without re-running** the
creation.

## Limitations

- **Multi-dialect across SQLite / PostgreSQL / MySQL** — the batch/move-and-copy gotcha and autogenerate blind spots confirmed against the Alembic docs at forge; treat exact command options as version-pinnable.
- **Sync-first** — the async `run_async_migrations` shape is covered as a short aside; most async stacks still migrate via a sync URL.
- **Sits on top of `sqlalchemy`** — it assumes a `Base.metadata` already exists and only wires Alembic to it; the schedule/queue schema lifecycle is `sql-job-queue`'s consumer concern.
