# a1 — platform boundary-resource documentation traversal

**Trigger:** always applicable. **Cap:** 12 — **ordering:** platform ecosystem size, then
documentation depth. **Sources:** `shopify-dev`, `vscode-api`, `slack-docs`, `chrome-ext`,
`wp-plugins`, `figma-plugins`, `notion-dev`, `zapier-platform`, `stripe-connect`,
`atlassian-marketplace`, `github-marketplace`. **Fallback:** `vscode-docs-repo`.

## Mechanism

Read each platform's own developer documentation for its **boundary resources** — the APIs, SDKs
and extension surfaces a complementor builds against. One platform at a time, its own text only.

## Query strategy

Enter through the platform's documentation root from the registry, then traverse to the sections
naming an extension surface. Do not search the open web for "how X's plugin API works": a
third-party explainer is a document containing no primary data, and citing it makes it the
load-bearing node in the evidence graph.

**Prefer the machine-readable variant, and RECORD WHICH ONE YOU READ.** `shopify.dev` serves
`<path>.md`; `docs.stripe.com` serves `<path>.md` and `llms.txt`. The variant is a channel with its
own death rate — Shopify's convention moved from `.txt` to `.md` inside eleven days — so the
variant read is part of the record, not an implementation detail.

## Unique coverage

The only angle that establishes WHAT a platform exposes at all. Every other angle presumes a
surface exists and asks something about it; this one enumerates the surface.

## What a candidate must carry

`platform_slug` from the wave-0 map, verbatim — never minted here. `source_id` of the registry row
actually read. `retrieved_at`. `as_of` when the content states when the fact became true, and NULL
when it does not — never defaulted to the fetch date.
