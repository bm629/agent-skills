# Angle a4 — code-content search

- **Mechanism:** searching the CODE ITSELF across public indexes — imports,
  identifiers, API signatures, config markers — instead of repository
  metadata. Finds implementations invisible to every metadata channel:
  poorly-described repos, sub-projects inside monorepos, forks carrying novel
  work.
- **Applicable group types:** per the registry; broadly `ecosystem_anchor`
  (the strongest — searching usage of anchor libraries), `technique`
  (algorithm/idiom identifiers), `capability` (capability-distinctive
  API/config markers).
- **Conditional:** none — always-on angle.
- **Sources (registry ids, tier order):** `sourcegraph`, `grep-app`,
  `github-code-search`.
- **last_verified:** 2026-07-17

## Unique coverage

Metadata search finds what authors chose to describe; code search finds what
they actually wrote. A repo named `my-project` with an empty README that
imports `ccxt`, subclasses `Strategy`, and ships a `backtest/` directory is
invisible to a1 and gold here.

## Query design — the heart of this angle

Code queries succeed on DISTINCTIVENESS. Derive query material from the
keyword map like this:

1. **From `ecosystem_anchor` groups** — the import/require forms:
   - Python: `import ccxt`, `from ccxt import`
   - JS/TS: `require('ccxt')`, `from 'ccxt'`
   - Config: the anchor's name in `pyproject.toml` / `package.json`
     dependency blocks (path-filtered queries below).
2. **From `technique` groups** — the identifiers practitioners actually
   name things: `def walk_forward`, `class MeanReversion`,
   `walk_forward_analysis(`, `zscore` near `spread`. Prefer snake_case AND
   CamelCase variants of the same concept (two queries).
3. **From `capability` groups** — capability-distinctive markers rather
   than the plain English word: `class Strategy` + `backtest` co-occurring;
   file-path markers (`path:backtest`), config keys (`stake_currency`,
   `timeframe` for trading bots).
4. **Negative terms** apply post-hoc: code search engines lack NOT
   semantics uniformly — scan results and count only in-domain hits,
   noting the filtering in the cell's query note.

Avoid: single common words (`backtest` alone floods), boilerplate
identifiers (`main`, `run`), anything under ~6 characters without a
qualifier.

## Source craft

### sourcegraph (tier 1)

`sourcegraph.com/search` over its public index (~2M+ repos). The richest
grammar of the three:

- Literal: `import ccxt lang:python count:100`
- Regex: `/def (run_|do_)?backtest/ lang:python`
- Structural (when precision matters): `strategy.backtest(:[args])`
- Filters that earn their keep: `lang:`, `file:` (path regex —
  `file:.*backtest.*\.py`), `repo:` (EXCLUDE known giants when hunting the
  tail: `-repo:^github\.com/freqtrade/`), `count:` (raise it — default
  truncates), `select:repo` (dedupe hits to one row per repository — USE
  THIS; candidates are repos, not lines).
- Worked example (`ecosystem_anchor` "ccxt"):
  - Pass 1: `import ccxt lang:python select:repo count:200`
  - Tail hunt: `import ccxt lang:python select:repo count:200
    -repo:^github\.com/(freqtrade|ccxt)/` — the leaders excluded, the
    unknown implementations remain.
- Worked example (`technique` "mean reversion"):
  - `/class \w*MeanReversion\w*/ select:repo`
  - `zscore lang:python file:.*strategy.* select:repo`
- Extraction: `select:repo` gives the repo list directly; open each repo's
  host page for signals (stars/license/flags) — the code hit itself goes
  into the relevance line ("imports ccxt in live-trading module").

### grep-app (tier 1)

Note for agent callers: grep.app also exposes an MCP (Model Context Protocol)
interface querying the same index — when your runtime has it connected, the
MCP surface is the ergonomic path (same coverage; record the queries in the
cell identically).

`grep.app` — fast literal/regex over a large GitHub slice. Plainer than
sourcegraph; excellent precision on exact strings.

- Filters: language, repo, path; case-sensitivity toggle; regex mode.
- Worked example: `from ccxt import` (language: Python) → the matched-repo
  sidebar IS the candidate list; note result counts per query.
- Its index is a subset — a zero here does not mean a zero exists;
  sourcegraph's cell covers the wider net (both cells recorded).
- Best for: exact idiomatic strings (`walk_forward`, `stake_currency`),
  config-file markers (search in path mode for `freqtrade.json`-style
  names when hunting a tool's ecosystem).

### github-code-search (tier 2)

GitHub's native code search (auth required for full power).

- Grammar: exact phrases in quotes; `language:`, `path:`, `repo:`, `org:`
  qualifiers; regex with `/.../ ` syntax.
- Worked examples:
  - `"import ccxt" language:python` — then flip to the Repositories tab of
    the result page to aggregate by repo.
  - `path:*.toml "backtesting"` — dependency-block hunting.
  - `/def walk_forward_\w+/ language:python`
- Rate limits: code search is the most limited GitHub surface (~10
  requests/min authenticated for the API; the UI throttles too) — batch
  slowly; a 429 is a retry, never a dead end.
- Fallback relationship: this is also a1's fallback for degraded repo
  search; when wearing THIS angle, use only code queries (the boundary
  holds even inside the same website — record repo-metadata leads in notes
  instead of running a1 queries).

## Aggregation to candidates

Code hits arrive line-grained; candidates are repo-grained:

1. Collapse hits per repository (sourcegraph `select:repo` does it; on
   grep-app/github use the repo sidebar/tab).
2. One candidate row per repo; `found_by.sources` lists each engine that
   hit it; the relevance line cites the strongest code evidence ("imports
   ccxt + implements Strategy subclass in strategies/").
3. Resolve signals from the repo's host page (stars, last commit, license,
   fork flags) — the code engines don't carry trustworthy metadata; the
   host page does. `as_of` = when you looked at the host page.
4. Vendored copies (the anchor's source pasted into `vendor/` or `lib/`)
   are hits on the anchor's own code, not users of it — recognize by path
   (`vendor/`, `node_modules/`, `third_party/`) and skip those hits (note
   the filtering once in the cell).

## Coverage duties

Cells per applicable (group × active a4 source). `domain` groups typically
owe nothing here (check the registry's `group_types` — plain domain nouns
make poor code queries); `ecosystem_anchor`/`technique`/`capability` groups
owe cells per active engine, zero-hits recorded with the exact queries
tried.

## Failure modes and fallbacks

- Index coverage varies wildly: grep-app misses what sourcegraph has and
  vice versa — that is WHY both are active; never mark a concept dead on
  one engine's zero.
- Rate limits (github-code-search especially): slow batches, backoff;
  `unreachable` only after retries.
- Regex flavor differences: sourcegraph RE2 (no backreferences), github
  RE2-ish, grep-app PCRE-lite — when a regex errors, simplify to literals
  rather than fighting the flavor; record the literal actually run.
- Query too broad (result flood): tighten with `lang:`/`path:`/`select:repo`
  and record the tightened query — never record the flood count as
  meaningful coverage.

## Candidate quality hints

Code-found candidates earn relevance lines with EVIDENCE ("subclasses
Strategy, 14 strategy files, imports ccxt") — that specificity is this
angle's whole value to the screening wave. A hit in tests-only
(`path:test_`) is weaker than a hit in the core module — say which.

## Worked end-to-end example (one group, all three engines)

Group `kw-anchor-ccxt` × a4's active engines:

1. sourcegraph: `import ccxt lang:python select:repo count:200` →
   ~120 repos; tail pass `-repo:^github\.com/(freqtrade|ccxt)/` → ~95
   unknown implementations. Cell queries record both strings + counts.
2. grep-app: `from ccxt import` (Python) → repo sidebar harvested; plus the
   exact-string pass `ccxt.pro` (the paid-tier import — its users are
   serious deployments; that observation goes in relevance lines).
3. github-code-search: `"import ccxt" language:python` → Repositories tab;
   plus `path:*.toml ccxt` for dependency declarations.
4. Merge per repo: `some-dev/exchange-bot` hit by all three engines →
   ONE candidate, found_by.sources lists all three, relevance line cites
   the strongest evidence ("imports ccxt in core + declares in
   pyproject").
5. Host-page resolution pass: signals + flags for each candidate repo,
   `as_of` stamped; vendored-copy hits (path `vendor/ccxt/...`) were
   skipped during aggregation and noted once.

## Query cookbook by group type

| Group type | Query shapes | Engines |
|---|---|---|
| ecosystem_anchor | `import X` / `require('X')` / `from X import` / dep-file mentions (`path:*.toml X`) | all three |
| technique | `def <technique_verb>` / `class <TechniqueNoun>` / distinctive constant names | sourcegraph (regex), grep-app (literal) |
| capability | co-occurring markers (`class Strategy` + path `backtest`), config keys | sourcegraph (structural), github (path:) |

Two variants per identifier concept (snake_case + CamelCase) is the default;
a third (kebab or SCREAMING) only when the ecosystem uses it.

## Time/budget shape

Anchor groups are this angle's payload: budget the deep passes there
(3-6 queries per engine). Technique groups get 2-3 distinctive-identifier
attempts per engine; capability groups 1-2 marker queries. When an engine
throttles, finish the group list before retrying the throttled one —
order within a source never matters, completeness does.

## Import-form reference by ecosystem

| Ecosystem | Import/require forms to query | Dep-file marker |
|---|---|---|
| Python | `import X` / `from X import` | `pyproject.toml`, `requirements.txt` |
| JS/TS | `require('X')` / `from 'X'` / `import X from` | `package.json` dependencies |
| Rust | `use X::` / `extern crate X` | `Cargo.toml` |
| Go | `"github.com/<owner>/X"` in imports | `go.mod` |
| Ruby | `require 'X'` | `Gemfile` |
| JVM | `import <groupid>.X` | `pom.xml`, `build.gradle` |

Query the forms matching the map's primary ecosystems; one canonical form
per secondary ecosystem (zeros recorded as always).
