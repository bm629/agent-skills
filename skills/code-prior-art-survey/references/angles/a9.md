# Angle a9 — platform registries/marketplaces (conditional)

- **Trigger condition:** the scope is anchored to a platform — it ships ON
  a platform (a VS Code extension, a WordPress plugin, a Home Assistant
  integration), or its domain's prior art natively lives in a platform
  registry (infrastructure → Terraform/Ansible; containerized services →
  Docker Hub). When false, no work; `sources.skipped` explains.
- **Mechanism:** searching the platform-native registry — where the
  platform's ecosystem publishes — and resolving entries to source repos.
  For platform-anchored scopes this beats every generic angle: the registry
  IS the domain's directory.
- **Applicable group types:** per the registry; broadly `domain`,
  `capability`, `ecosystem_anchor` (docker-hub).
- **Sources (registry ids, tier order; each carries its OWN sub-condition):**
  `docker-hub`; `artifact-hub` (kubernetes-adjacent); `terraform-registry` +
  `ansible-galaxy` (infrastructure); `vscode-marketplace`
  (editor-extension); `wordpress-plugins` (wordpress-adjacent);
  `home-assistant-hacs` (home-automation); `homebrew` (cli-tool);
  `flathub` + `snapcraft` (desktop-app); `f-droid` (android); `pub-dev`
  (flutter/dart).
- **last_verified:** 2026-07-17

## Unique coverage

Platform-native prior art invisible elsewhere: a Home Assistant integration
lives in HACS, not on anyone's awesome list; the definitive Postgres
container patterns live in Docker Hub image repos. Also the only angle that
surfaces DISTRIBUTION prior art — how comparable projects package/ship on
the platform the scope targets.

## Sub-condition resolution (do this first)

Per active a9 source, check its registry `conditional` against the scope
context. Typically 1-3 of the twelve fire for a given platform-anchored
scope; the rest belong in the map's `sources.skipped` (if the map lists
them active anyway, work them — the map is the contract — but note the
mismatch for the next revision). Every fired source gets the full group
sweep; the craft per source:

## Source craft

### docker-hub (tier 1 — containerized-service scopes)

1. `hub.docker.com` search per domain/capability term; filters: official
   images, verified publishers, then the open sea (the no-floor layer —
   community images with real pulls).
2. Per hit: pull-count (adoption analog → relevance line) + the image
   page's linked source repo (Dockerfile link / GitHub badge) → the repo
   candidate. Images without source links: hub-page candidate
   (`host: docker-hub`) with a "source not linked" note.
3. Worked example (domain "trading bot"): search `trading bot`, `freqtrade`
   (anchor term) → official-ish images + forks; the FORK images with real
   pulls reveal deployment variants worth recording ("fork image, 500k
   pulls — deployment-hardened variant").
4. Tags/labels on images (`org.opencontainers.image.source`) resolve repos
   when the page doesn't.

### artifact-hub (tier 2 — kubernetes-adjacent)

1. `artifacthub.io` search per term; kind filters (Helm charts, operators,
   plugins).
2. Charts declare their `sources:` links — resolve to repos; chart
   popularity (stars on artifact-hub) → relevance line.
3. An operator/chart for a comparable product is architecture prior art
   (how the domain deploys) — frame relevance lines accordingly.

### terraform-registry + ansible-galaxy (tier 2/3 — infrastructure scopes)

1. `registry.terraform.io`: providers + modules per term; per hit the
   GitHub repo is directly linked (registry requires it). Download counts
   → relevance lines.
2. `galaxy.ansible.com`: roles/collections per term; same resolution.
3. For a scope BUILDING infra tooling these are the domain directory; for
   a scope merely DEPLOYED on infra they usually stay skipped — the
   sub-condition text in the registry is the judge.

### vscode-marketplace (tier 2 — editor-extension scopes)

1. `marketplace.visualstudio.com` search per term + `open-vsx.org` (the
   FOSS mirror — some extensions publish only there). Two surfaces, ONE
   registry entry, ONE cell — record both surfaces' queries in it.
2. Per hit: install count + the extension page's repository link →
   candidate. Marketplace-only extensions (no repo): hub-page candidates,
   noted.
3. Extensions ARE the product form for editor scopes — coverage here is
   the domain sweep, not a supplement.

### wordpress-plugins (tier 3 — wordpress-adjacent scopes)

1. `wordpress.org/plugins` search per term; active-install counts (the
   honest adoption number) + last-updated; the plugin page links its
   development repo (or the wordpress.org SVN — record it as the repo
   with a note when no Git mirror exists).
2. The plugin ecosystem's review section carries failure lore — one clause
   for relevance lines when it is loud.

### home-assistant-hacs (tier 3 — home-automation scopes)

1. HACS default repositories list (a curated GitHub-org-shaped catalog) +
   `hacs.xyz` search per term; entries are GitHub repos directly.
2. Community forum threads pin the de-facto standards — one reconnaissance
   pass, names resolved as usual.

### homebrew (tier 3 — cli-tool scopes)

1. `formulae.brew.sh` search per term; formula pages link upstream repos
   directly + carry install analytics (30/90/365-day) → relevance lines.
2. A formula's existence is itself a maturity signal ("packaged in
   homebrew-core") — say it.

### flathub + snapcraft (tier 3 — desktop-app scopes)

1. `flathub.org` + `snapcraft.io` search per term; app pages link upstream
   repos; install/download stats where exposed.
2. Two surfaces, two registry entries, two cells — their populations
   differ (GNOME/KDE-leaning vs Ubuntu-leaning).

### f-droid (tier 3 — android scopes)

1. `f-droid.org` search per term — FOSS-only by construction, every entry
   links source; the catalog's metadata includes anti-features flags
   (worth a relevance clause).

### pub-dev (tier 3 — flutter/dart scopes)

1. `pub.dev` search per term; scores (likes/pub points/popularity) +
   linked repos; the platform-native package layer for Flutter scopes.

## Coverage duties

Cells per (applicable group × FIRED active source) — the sub-condition
narrows which of the twelve owe cells for a given run; the map's
`sources.active` is still the outer contract. Zero-hits recorded with
queries; a fired-but-zero platform source is a real market finding ("no
Home Assistant integration exists for X" — note it as such).

## Failure modes and fallbacks

- Registry pages without source links: hub-page candidates with the gap
  noted — platform registries vary wildly in enforcing source linkage.
- Install/pull counts hidden or estimated: record what the page shows with
  `as_of`; never extrapolate.
- Platform registry search is name-biased (weak description search):
  compensate with category browsing where the registry has categories
  (docker-hub categories, wordpress plugin categories) — record the
  category walked as the query.
- A platform's registry blocks anonymous browsing intermittently: retry,
  switch surface (API vs UI), then `unreachable` with the attempt.

## Candidate quality hints

Platform metrics are adoption-analogs, not `signals.downloads` unless the
registry literally reports downloads — put pulls/installs/active-installs
in the relevance line with their name ("2M docker pulls", "40k active
installs"). Distribution-form observations ("ships as single container,
config via env") are extraction-wave gold — one clause now, the deep read
later.

## Worked end-to-end example

Scope: self-hosted trading bot (containerized service → docker-hub +
artifact-hub fire; the other ten stay skipped with reasons).

1. docker-hub: `trading bot` + anchor term `freqtrade` → 7 images → 4
   repo-resolved candidates (2 deployment-variant forks flagged as forks,
   honest), 1 hub-only.
2. artifact-hub: `trading` → 1 Helm chart (community, for freqtrade) →
   candidate with "deploys the leader on k8s — architecture prior art"
   relevance line.
3. Cells: both sources × applicable groups (domain, capability,
   ecosystem_anchor per registry group_types), zeros included.

## Distribution-observation capture

Unique to this angle: HOW comparable projects ship. Per strong candidate,
one clause on distribution form ("single container + env config",
"helm chart with 3 subcharts", "brew formula, no service management") —
downstream architecture design consumes these directly, and no other angle
sees them.

## Registry-metadata trust rubric

Platform registries self-report differently: docker pulls (inflated by CI),
wordpress active-installs (solid), marketplace installs (solid), brew
analytics (opt-in undercount). One clause of calibration when citing a
number ("2M pulls — CI-inflated metric") keeps relevance lines honest.
