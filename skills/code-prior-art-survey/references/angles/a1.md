# Angle a1 — host metadata search

- **Mechanism:** keyword + operator search against code-hosting platforms'
  repository metadata (names, descriptions, topics, READMEs-as-indexed).
- **Applicable group types:** per the registry entries for a1 — consult
  `references/source-registry.yaml`; broadly `domain`, `capability`,
  `technique`, `ecosystem_anchor`, `competitor` (per-source variation applies).
- **Conditional:** none — always-on angle.
- **Sources (by registry id, tier order):** `github`, `gitlab`, `codeberg`,
  `bitbucket`, `sourceforge`, `sourcehut`, `gitee` (conditional). Craft per
  source below; the list itself lives ONLY in the registry.
- **last_verified:** 2026-07-17

## Unique coverage

The broad cast: anything with a well-described repository. Other angles find
what metadata search misses (poorly-described repos → a4; whole products vs
competitors → a5; adoption ground truth → a3) — do not chase those here.

## The tiered-pass discipline (applies to every source in this angle)

1. **Pass 1 — ranked quality pass.** Use quality operators (stars, recent
   pushes) to surface the visible leaders per query. This pass RANKS; it
   never decides existence.
2. **Pass 2 — no-floor pass.** Re-run every `capability` and `technique`
   group query with NO popularity operator (keep only a recency filter per
   the map's `filters.recency`). This is where the two-star hidden gem
   surfaces. Skipping this pass violates the map's `popularity_floor: none`
   contract.

Record each pass's queries in the same coverage cell for the (group × source)
pair — exact strings, timestamp, and ONE summed result_count (integer;
per-query counts, if worth keeping, ride in a `note:` query string — see the
search-output guide's annotation convention).

## Source craft

### github (tier 1)

The richest operator grammar. Work each keyword group through three surfaces:

1. **Repository search** — worked examples for a `capability` group
   (canonical "backtesting", expansions "walk-forward testing",
   "historical simulation"):
   - Pass 1: `backtesting language:python pushed:>2024-07-01 stars:>50`
   - Pass 1 expansion: `"walk-forward" language:python pushed:>2024-07-01`
   - Pass 2 (no-floor): `backtesting pushed:>2024-07-01` — then scan pages
     2-5, not just page 1; small repos live deep.
   - Operator notes: `in:name,description,readme` widens matching;
     `topic:backtesting` hits the folksonomy; `NOT` excludes negative terms
     (`backtesting NOT cards`); quote multi-word terms; `archived:false`
     may be used in Pass 1 ranking but never to drop candidates from Pass 2
     (archived repos still carry patterns — record them with the
     `archived: true` flag instead).
2. **Topic pages** — `github.com/topics/<term-slug>` for every canonical term
   and probe-discovered term (`topics/algotrading`, `topics/backtesting`).
   Topics are community-assigned — high precision, and the "related topics"
   strip is free vocabulary discovery (record new terms in notes, do not
   search them).
3. **Curated platform surfaces** — Trending (filter by the map's language(s),
   weekly + monthly windows) and Collections when a relevant one exists.
   These are ranking-only surfaces: treat as Pass-1 supplements.

Candidate extraction: repo URL, name, description (verbatim), primary
language, stars, last push, license, `archived`/`is_fork`/`fork_of` (fork
status is on the repo page and in API responses — record it; forks are not
independent findings). Rate limits: authenticated search ≈ 30 requests/min —
batch queries with short delays; on a 403/429, back off and retry (a rate
limit is never a dead end; only record `unreachable` after retries fail).

Fallback: if repository search degrades, `github-code-search` (angle a4's
registry entry) covers the content side — note the degradation, do NOT run
a4's mechanism yourself.

### gitlab (tier 2)

Projects search at `gitlab.com/explore` (or API `projects?search=`). Grammar
is plainer than GitHub's: keyword matching on name/description/tags, sort by
stars or last activity.

- Worked example (`domain` group): explore search `trading bot`, sort
  `stars_desc` (Pass 1); re-run sorted by `latest_activity_desc` with no
  star attention (Pass 2).
- GitLab hosts a distinct population: enterprise-adjacent and
  privacy-leaning projects that never mirror to GitHub — expect lower volume
  but genuinely unique hits; a zero here is normal for niche domains
  (record it).
- Topics exist (`gitlab.com/explore/projects/topics/<term>`) but are far
  sparser than GitHub's — try canonical terms only.
- Signals available: stars, last activity, license (often absent from search
  results — leave null rather than guessing).

### codeberg (tier 2)

Forgejo-based, EU/nonprofit; privacy-conscious projects, some GitHub
emigrants. Search at `codeberg.org/explore/repos`.

- Worked example: `backtesting` in the explore search, default relevance,
  then sorted `recentupdate` for the no-floor pass. Star counts are tiny
  platform-wide — never apply a star operator here at all; recency is the
  only meaningful filter.
- Topic search exists (`explore/repos?q=<term>&topic=1`) — worth one query
  per canonical term.
- Expect single-digit result counts in most domains; a small population
  makes each hit disproportionately interesting (these repos chose to be
  off-GitHub — often mature maintainers).

### bitbucket (tier 3)

Weakest search of the majors: `bitbucket.org/repo/all?name=<term>` matches
names primarily. One pass per canonical term + strongest expansion is
proportionate; deep expansion sweeps are wasted here.

- Worked example: repo search `trading-bot`, then `backtesting`.
- Population skews Atlassian-ecosystem/enterprise and Java-heavy legacy;
  public volume dropped after Mercurial sunset — zeros are common and
  expected. Record them.

### sourceforge (tier 3)

Legacy pioneer; still authoritative for pre-2015 projects and certain
scientific/desktop niches. Search `sourceforge.net/directory/?q=<term>` and
the category directory.

- Worked example: directory search `trading`, category filter
  `Office/Business :: Financial`, sort by activity.
- Read the project page's "Activity" and last-file date — many entries are
  fossils; a fossil with a unique pattern still counts (record with its
  dates; the screening wave judges).
- Extraction: SourceForge project pages often link an upstream Git repo —
  record that as the canonical `repo` URL when present; else the SF project
  URL with `host: sourceforge` and the owner-less id convention
  (`sourceforge__<project>__<project>` — see the search-output guide).

### sourcehut (tier 3)

`sr.ht/projects` search; minimalist metadata (no stars at all — signals:
last activity only, leave popularity fields null).

- Worked example: project search per canonical term; one query per group is
  proportionate.
- Population: email-workflow purists, systems tooling; expect zeros outside
  infra/dev-tool domains — record them.

### gitee (tier 3 — conditional)

Activate only when the registry condition holds (significant CJK-ecosystem
footprint for the domain — a scope-context judgment; `filters.languages`
lists programming languages and does not answer this). When active:

- Search `gitee.com/explore` per canonical term; add zh-translated terms
  ONLY if the map carries them as expansions (never invent translations —
  that is a map defect to note, not improvise).
- When inactive for the run, it must appear in the map's `sources.skipped`
  with the reason; if the map forgot it, record the gap in notes.

## Coverage duties

One cell per (applicable group × source above that is in `sources.active`),
zero-hits included. For this angle "applicable" spans most group types —
check each source's `group_types` in the registry rather than assuming; e.g.
`community` groups are NOT host-search material (no cell owed), and
`competitor` groups are worked as name searches (finding clones/forks of the
competitor — flag them honestly).

## Failure modes and fallbacks

- Rate limits (github): back off + retry; only `unreachable` after retries.
- A host's search UI/API changes: try the alternate surface (UI vs API) —
  record what worked in the coverage cell's query string; note the drift for
  the registry maintainer.
- A host is down: record in `notes.unreachable_sources` with the attempt;
  its registry `fallbacks` name where equivalent coverage partially exists —
  do not silently claim the fallback covered it (different mechanisms find
  different things; the cell stays a recorded gap).

## Candidate quality hints (ranking within your output, never exclusion)

Prefer for top ranks: descriptions that name the domain precisely; recent
activity; a real license; non-fork status. Push down (never drop): tutorial
repos ("built following X course" — record, note the smell in relevance),
empty shells, obvious homework. The screening wave applies the real quality
filter — your relevance line and honest signals are what it works from.

## Per-group-type query patterns (quick reference)

| Group type | Pattern shape | Worked example |
|---|---|---|
| domain | bare + qualified product nouns | `"trading bot"`, `algotrading framework` |
| capability | the capability + implementation nouns | `backtesting engine`, `"walk-forward" library` |
| technique | technique + language/domain qualifier | `"mean reversion" python`, `"pairs trading" strategy` |
| ecosystem_anchor | anchor name + built-on phrasing | `ccxt bot`, `"built on ccxt"`, `topic:ccxt` |
| competitor | competitor name + open/clone phrasing | `"tradingview" alternative`, `quantconnect open source` |

Negative terms attach per the group: `trading NOT cards NOT sports` (GitHub),
or post-filter results where the host has no NOT operator (gitlab, codeberg —
filter by eye, count only in-domain hits, and say so in the cell's query
note).

## Worked end-to-end example (one group, one source)

Group `kw-cap-backtesting` (canonical "backtesting"; expansions
"walk-forward testing", "historical simulation", "paper trading") × source
`github`:

1. Pass 1 queries (recorded verbatim in the cell):
   - `backtesting language:python pushed:>2024-07-01 stars:>50`
   - `"walk-forward" language:python pushed:>2024-07-01 stars:>25`
   - `"paper trading" language:python pushed:>2024-07-01`
2. Topic surface: `github.com/topics/backtesting` (note related topics:
   `quant`, `trading-strategies` → vocabulary notes).
3. Pass 2 no-floor:
   - `backtesting language:python pushed:>2024-07-01` — pages 1-5
   - `"historical simulation" trading` — no language filter (catches
     multi-language repos), pages 1-3
4. Cell recorded: 6 query strings, timestamp, summed result_count; the 8-12
   most relevant hits become candidate rows with full signals; a repo found
   twice (query + topic) is ONE candidate whose found_by lists both.
5. Time budget: ~10-15 minutes for a rich group × github; the long tail
   sources get proportionally less (bitbucket: 2-3 minutes).

## Extraction mapping (host page → candidate record)

- `id`: lowercase host + `__` + owner + `__` + name, verbatim case for
  owner/name (`github__kernc__backtesting.py`).
- `description`: the repo's About line, verbatim — even when unflattering.
- `language`: the host's primary-language stat; null when absent.
- `flags`: fork banner → `is_fork` + `fork_of` (upstream slug); "mirror of"
  in description → `is_mirror`; archive banner → `archived`.
- `signals`: stars, last push date (host UI), license (About box), downloads
  null (registry angles own downloads), `as_of` = when YOU looked.
- `relevance`: one line, scope-grounded, mentioning the pass that found it
  when informative ("no-floor pass; 40 stars but implements walk-forward
  natively").
