# Angle a7 — academic/research code (conditional)

- **Trigger condition:** the scope is algorithm-heavy or ML-involved — the
  caller's scope context names techniques with research literature behind
  them, or an ML capability exists. When the trigger is false for a run,
  this angle spawns no work and the map's `sources.skipped` explains it.
- **Mechanism:** finding the CODE behind research — papers with linked
  implementations, research-software archives, paper→code resolvers. State
  of the art often ships here months before productized repos exist.
- **Applicable group types:** per the registry; broadly `technique` (the
  star), `capability`, `domain`.
- **Sources (registry ids, tier order):** `arxiv`, `semantic-scholar`,
  `hf-papers`, `catalyzex`, `opencodepapers`, `openreview`, `zenodo`.
- **last_verified:** 2026-07-17

## Unique coverage

Pre-productization implementations: the reference implementation of the
exact algorithm the scope names, written by its authors. Weaker on
engineering polish, unmatched on algorithmic fidelity — say so in relevance
lines ("author reference implementation; research-grade code").

## Historical caution baked into this angle

The field's canonical hub (Papers With Code) was shut down abruptly in
mid-2025 — its successors are fragmented and none is complete. That is why
this angle works MULTIPLE resolvers and records zeros honestly: no single
source is trusted to be the index anymore. If a source here dies, the
registry fallback chain is the recovery path, and the brief notes the drift
for the registry maintainer.

## Source craft

### arxiv (tier 1)

1. Per `technique` group: `arxiv.org` search (all fields) for canonical +
   expansions; categories filter when obvious (`q-fin.TR` for trading,
   `cs.LG` for ML).
2. Worked example (technique "mean reversion"):
   - `arxiv search: "mean reversion" trading` (recent-first + relevance
     passes — the recent pass is this angle's no-floor analog: new papers
     have no citations yet, and citation-count worship is the popularity
     floor of academia).
3. Per hit: hunt the code link — abstract-page "Code" tab (arXiv surfaces
   linked repos), the PDF's footnotes/appendix ("code available at…"),
   or the authors' pages (one hop max).
4. A paper WITHOUT code: the technique + author names go to notes as a
   lead ("paper exists, no code found — potential gap/novelty signal");
   papers are never candidates themselves.
5. Extraction: resolved repos get normal candidate rows; the relevance line
   cites the paper ("implements <paper title, year>").

### semantic-scholar (tier 1)

1. Same technique-term queries via `semanticscholar.org`; its strength is
   the citation graph + "code" artifact links on paper pages.
2. Use the citation hop ONCE per strong paper: highly-cited papers' citing
   works often contain the maintained follow-up implementation (the
   original's code may be frozen; the citing survey's repo is alive).
3. API exists (rate-limited, no key for low volume) — polite batching;
   record per-query counts.

### hf-papers (tier 2)

`huggingface.co/papers` — trending papers with linked models/repos/spaces.

1. Search per technique term; strongest for ML-adjacent scopes.
2. A paper page's linked artifacts (model, space, GitHub) resolve directly —
   harvest the GitHub links as candidates; model/space links matter to a8
   (note them for the a8 scout rather than working them here — boundary).
3. Trending bias = recency bias — fine; this source is the fresh layer,
   the archives above are the deep layer.

### catalyzex (tier 2)

`catalyzex.com` — paper→code resolver (a Papers-With-Code successor).

1. Query per technique term AND per specific paper title found upstream
   (arxiv/semantic-scholar hits without visible code get one catalyzex
   lookup each — it indexes implementations the paper page missed,
   including third-party reimplementations).
2. Third-party reimplementations are first-class candidates — often better
   engineered than author code; relevance line says "third-party
   implementation of <paper>".

### opencodepapers (tier 3)

Community-maintained paper→code lists (successor efforts to the shuttered
hub). Coverage is partial and uneven:

1. One lookup per technique term; treat as a cross-check layer — its
   unique value is community-verified pairings.
2. Expect zeros often; record them. When it disagrees with catalyzex on a
   paper's implementation, record both repos (both are candidates; the
   screening wave compares).

### openreview (tier 3)

`openreview.net` — venue submissions with reviews, often pre-camera-ready.

1. Venue-scoped searches per technique term (ICLR/NeurIPS/ICML for ML
   scopes; domain venues otherwise).
2. Submissions link code for reproducibility review increasingly often —
   the "supplementary" section is the place to look.
3. Reviews themselves sometimes name better prior implementations
   ("this duplicates X") — mine top reviews of strong hits for names
   (resolution discipline as usual).

### zenodo (tier 3)

`zenodo.org` — the research-software archive (DOI-stamped releases).

1. Search per technique + domain term, filter type=software.
2. Hits are SNAPSHOTS (archived versions) — resolve to the living repo via
   the record's metadata links; the DOI + version go in the relevance line
   (a DOI'd release signals reproducibility discipline — a real quality
   marker for research code).
3. When only the archive exists (no living repo), the zenodo record URL is
   the `repo` with `host: zenodo` and the owner-less id convention
   (`zenodo__<record-id>__<slug>`) — record its frozen-ness honestly.

## Coverage duties

Cells per applicable (group × active a7 source), applicability being
exactly each source's `group_types` in the registry — check them, never
assume (technique groups owe the most sources; domain groups the fewest).
Zero-hits with query strings recorded;
"paper found, code absent" zeros carry that note (it is a different zero
than "no papers").

## Failure modes and fallbacks

- Resolver disagreement (catalyzex vs opencodepapers vs the paper page):
  record every distinct repo found — disagreement is data, dedup happens
  downstream.
- Paywalled venues: arXiv preprints cover most CS/quant work; a paywalled
  paper with no preprint → notes lead, never a guessed implementation.
- Author code links rot fast (lab pages die): one archive.org lookup is
  the permitted rescue attempt; else notes with the paper reference.
- Wrong-field homonyms ("mean reversion" in ecology): negative terms +
  category filters; note the filtering.

## Candidate quality hints

Research code needs honest framing: "author implementation, last commit =
paper camera-ready date, no tests" is a NORMAL and valuable candidate —
the relevance line carries algorithmic fidelity ("reference impl of the
exact walk-forward variant the scope names") while the signals carry the
engineering reality. Never let research-code roughness push a candidate
out at this stage; the screening wave weighs it with the rescue rule in
reach.

## Worked end-to-end example

Group `kw-tech-mean-reversion` × the a7 sweep:

1. arxiv: `"mean reversion" trading` (relevance + recent passes) → 14
   papers; 5 with code links → 5 candidates; 9 code-less → 3 worth
   catalyzex lookups.
2. catalyzex: those 3 titles → 1 third-party implementation found →
   candidate ("third-party impl of <title>").
3. semantic-scholar: same term → citation hop on the strongest paper →
   a maintained successor repo → candidate.
4. hf-papers/openreview/opencodepapers/zenodo: one query each → zeros
   except zenodo (1 DOI'd release resolving to a live repo).
5. Net: 8 candidates, each with paper-grounded relevance lines; cells for
   all 7 sources including the 3 zeros.

## Paper-quality triage (which papers earn resolution effort)

| Signal | Weight |
|---|---|
| venue/peer review (vs preprint-only) | medium — preprints fine in fast fields |
| citations for its age | medium — never a floor (new papers = no citations) |
| authors ship code historically | high — check one author's profile |
| reproducibility artifacts (DOI, checklist) | high |
| survey papers | special: mine their tables for implementation lists — a survey's comparison table is a pre-built candidate list |

Triage caps resolution effort per group (~10-15 papers deep-checked);
beyond that, titles + zero-cells tell the story honestly.

## Survey-paper mining (the shortcut worth its own section)

One good survey ("A survey of algorithmic trading frameworks, 2024") often
carries a comparison table of every implementation the field knows. Search
`survey <canonical>` / `review <canonical>` on arxiv + semantic-scholar
FIRST; when found, its table entries become resolution targets and the
relevance lines cite both survey and original ("listed in <survey>;
author impl of <paper>"). This is the highest-yield single move in the
academic angle.

## Trigger-decision worked note

Scope "ai-quant trading bot": techniques (mean reversion, walk-forward) have
research literature + an ML signal capability exists → trigger TRUE, full
sweep. Counter-example scope "self-hosted bookmark manager": no
research-backed techniques, no ML → trigger FALSE, angle spawns nothing,
map skips a7 sources with reason "no algorithm-heavy/ML scope".

## Resolution-effort budget (keeps the angle bounded)

Per technique group: survey hunt (1-2 queries) -> tier-1 sweeps -> ~10-15
papers deep-checked for code -> resolver lookups for the code-less strong
ones -> tier-3 single passes. Roughly 30-45 minutes per rich technique
group; capability/domain groups take the lighter tier-1-only sweep. Record
where the budget stopped ("checked top 12 of 31 papers") — bounded honesty
beats unbounded pretense.
