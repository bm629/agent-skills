# Angle a3 — package registries + dependents graph

- **Mechanism:** two complementary moves over package-ecosystem data:
  (1) registry keyword/statistics search — what packages exist for the
  domain's terms, weighted by real download adoption; (2) dependents-graph
  walking — what projects BUILD ON the map's `ecosystem_anchor` libraries.
  Both find what is USED, not merely starred.
- **Applicable group types:** per the registry; broadly `domain`,
  `capability`, `technique`, `ecosystem_anchor` — the dependents sources
  (`deps-dev`, `github-used-by`) consume ONLY `ecosystem_anchor` groups;
  most registry-search sources consume `ecosystem_anchor` too (the anchor
  NAME as a keyword).
- **Conditional:** the angle is always-on; `conda-forge` is
  domain-conditional.
- **Sources (registry ids, tier order):** `pypi`, `npm`, `libraries-io`,
  `ecosyste-ms`, `deps-dev`, `github-used-by`, `crates-io`, `pkg-go-dev`,
  `maven-central`, `rubygems`, `packagist`, `nuget`, `hex-pm`,
  `conda-forge` (conditional).
- **last_verified:** 2026-07-17

## Unique coverage

Adoption ground truth. A library with 400k monthly downloads and no GitHub
glamour is real prior art; a repo importing an anchor library is a working
implementation whether or not its README sells it. This is also the angle
where `package` fields get filled — always record the registry + package
name so downstream stages can cross-reference.

## Language-ecosystem scoping (do this first)

The map's scope context implies the relevant language ecosystems (a Python
trading bot → pypi + conda-forge matter; npm marginal). Work ALL active a3
sources — but proportionately: primary ecosystems get the full group sweep;
secondary ones get canonical-term passes, and their zeros are expected and
recorded. Never skip a source silently because "wrong language" — that
judgment goes in the coverage cell's query note or the map's
`sources.skipped` next revision.

## Source craft — registry search side

### pypi (tier 1)

1. Keyword search (`pypi.org/search`) per canonical + expansions; the search
   is weak on relevance — also grep the monthly top-packages dump (the
   `top-pypi-packages` dataset, ~15k packages by downloads) for term
   matches: `grep -i backtest top-pypi-packages.json`.
2. Per hit: resolve the package page → `codeRepository`/homepage link → the
   candidate repo. Record `package: {registry: pypi, name: <pkg>}` and
   downloads (pypistats or the dump's number) with `as_of`.
3. Worked examples (`capability` group "backtesting"):
   - `pypi.org/search/?q=backtesting` (Pass 1, relevance order)
   - top-packages grep: `backtest|walk.?forward` (adoption order)
   - classifier browse when apt: `Topic :: Office/Business :: Financial`
4. A package with no public repo link: record it with the pypi URL as
   `repo` and note "no public source" — screening will likely discard, but
   the existence signal is real.

### npm (tier 1)

`npmjs.com/search?q=<term>` + npmtrends for download comparison of the top
hits. Same resolution flow (package → repository field → candidate). npm's
keyword spam is notorious: lean on weekly downloads to rank, and let obvious
name-squatters through with an honest low-relevance line rather than
silently dropping (they cost one row).

### libraries-io (tier 1)

Cross-registry: keyword search across 36 package managers in one place —
`libraries.io/search?q=<term>` (+ `platforms=` filter). Use it (a) as the
sweep for ecosystems with no dedicated source entry active, (b) to
cross-check a package's SourceRank + dependents count. API exists (key
needed); the web UI suffices for survey volumes.

### ecosyste-ms (tier 1)

Open APIs, no key: `packages.ecosyste.ms` (package search + per-package
dependents), `repos.ecosyste.ms` (repo metadata). Machine-friendly sweep:
one API query per canonical term per primary ecosystem; harvest
names + repo URLs + latest-release recency. Be polite (~1 req/s). Also the
fallback surface for most other a3 sources — note in the cell when used as
a fallback for a down source.

### crates-io / pkg-go-dev / maven-central / rubygems / packagist / nuget / hex-pm (tiers 2-3)

The per-ecosystem long tail — same craft, condensed: keyword search per
canonical term (+ strongest expansion for primary ecosystems); resolve to
source repos; record downloads where exposed (crates.io: yes; pkg.go.dev:
imported-by count instead — record it as the downloads-analog in the
relevance line, leave `downloads` null; maven: no meaningful count — null).
Zeros in off-language ecosystems are expected; record them. pkg.go.dev
bonus: the `imported-by` page for any anchor-adjacent Go package doubles as
a mini dependents graph.

### conda-forge (tier 3 — conditional: scientific/data-python domains)

`anaconda.org/conda-forge` channel search per canonical term. Mostly
mirrors pypi hits — a "same packages as pypi" dead-end note is the normal
outcome when it is active; record it once and keep the cells honest.

## Source craft — dependents side (`ecosystem_anchor` groups only)

### deps-dev (tier 1)

Google's Open Source Insights. For each anchor library (e.g. `ccxt`):

1. Resolve the anchor on `deps.dev` (system + package name).
2. Walk its DEPENDENTS (direct first — transitive explodes; direct
   dependents are the "built on top of it" set).
3. Rank dependents by their own adoption (the page exposes each dependent's
   version/scorecard data; stars come later from the host page).
4. Record top ~20-30 as candidates with `found_by.sources: [deps-dev]`,
   plus the anchor group id. Worked query string for the cell:
   `"deps.dev dependents of ccxt (PyPI), direct, first 3 pages"`.
5. Edge: monorepos publishing many packages appear as many dependents —
   collapse to the repo (the canonical id dedups them) and say so in notes.

### github-used-by (tier 2)

The Dependents tab on the anchor's GitHub page (`/network/dependents`).
Public repos only; sortable neither well nor stably — walk the first pages
and harvest repos with visible stars first, then a no-floor page sweep
(the low-star pages are exactly where unknown real implementations live).
The tab is HTML-only (no API) — record page counts walked in the query
string for reproducibility. Fallback: `deps-dev` (and vice versa — they
disagree at the margins; both cells exist when both are active).

## Coverage duties

Cells per applicable (group × active source), applicability being exactly
each source's `group_types` in the registry (dependents sources list only
`ecosystem_anchor`; the registry-search sources vary — check, never
assume). Zero-hits everywhere are recorded, never omitted.

## Failure modes and fallbacks

- Registry search APIs rate-limit or captcha: retry with backoff; switch
  UI↔API surface; only then `unreachable` + registry fallback noted.
- Download stats unavailable (service down): record signals with nulls +
  `as_of`, note the gap — never guess numbers.
- Package → repo resolution dead (404 repo link): keep the package-page URL
  as `repo`, note the rot; it may be renamed — one name search on the host
  is the permitted resolution attempt (a1-style single lookup, not a1's
  mechanism).
- Anchor library not on deps.dev (unsupported ecosystem): record the cell
  as zero with the attempt; `github-used-by` is the fallback for the same
  anchor.

## Candidate quality hints

Downloads + a live repo + a recent release ranks top. Dependents-found
candidates carry an implicit "actually uses the anchor" endorsement — say
which anchor in the relevance line ("direct dependent of ccxt"). Wrappers
and thin forks surface a lot here: honest flags + a relevance line that
says "thin wrapper around X" keep the record useful without dropping it.

## Worked end-to-end example (dependents side)

Group `kw-anchor-ccxt` (anchor library `ccxt`) × source `deps-dev`:

1. Resolve: deps.dev → system PyPI → package `ccxt` (also exists for npm —
   when the map's ecosystems include JS, BOTH resolutions are worked and the
   cell's query string names each).
2. Walk direct dependents, 3 pages, adoption-ranked: query string recorded
   as `"deps.dev dependents of ccxt (PyPI), direct, pages 1-3"`.
3. Harvest: `freqtrade` (dependent, huge adoption), `jesse` (dependent),
   ~20 more; each candidate's found_by = `{group_ids: [kw-anchor-ccxt],
   sources: [deps-dev]}` and the relevance line opens "direct dependent of
   ccxt — ...".
4. Cross-check on `github-used-by` (`ccxt/ccxt/network/dependents`): first
   3 star-visible pages + 2 no-floor pages; the disagreement margin (repos
   on one surface but not the other) is normal — both cells recorded, both
   found_by entries honest.
5. Monorepo collapse: `some-org/trading-platform` appears 3× via its
   published sub-packages → ONE candidate (canonical repo id), noted.

## Worked end-to-end example (registry-search side)

Group `kw-cap-backtesting` × source `pypi`:

1. `pypi.org/search/?q=backtesting` — top 3 pages; per hit open the package
   page, capture monthly downloads (pypistats) + the repo link.
2. Top-packages dump grep: `grep -iE "backtest|walk.?forward"
   top-pypi-packages.json` → adoption-ordered hits the search buried.
3. Expansions: `walk-forward`, `historical simulation` (quoted), `paper
   trading` — one search each; most yield subsets, recorded per query
   string in the same cell.
4. Candidates: `backtesting` (kernc), `vectorbt`, `zipline-reloaded`
   (found ONLY via the dump — its search rank is poor; the relevance line
   says so: "high downloads, low search rank — adoption-found").
5. Package field: `{registry: pypi, name: backtesting}` etc.; downloads +
   `as_of` stamped from pypistats at query time.

## Ecosystem-proportionality worked decision

Scope: Python-primary trading bot. Active a3 sources worked as:
- FULL sweep (all groups, all expansions): pypi, libraries-io, ecosyste-ms,
  deps-dev, github-used-by.
- Canonical-only pass: npm (JS bots exist — real but secondary), crates-io
  (rust trading is a real niche), pkg-go-dev.
- Canonical single query, zeros expected: maven-central, rubygems,
  packagist, nuget, hex-pm — the zero cells take seconds each and complete
  the contract honestly.
This decision (which got full vs light treatment and why) is recorded in
one line inside notes.dead_ends or the relevant cells' query notes — the
reviewer should see proportionality was a decision, not neglect.

## Signals hygiene specific to this angle

- Downloads are per-registry and per-window (pypistats = last month; npm =
  weekly) — record the number you saw and let `as_of` carry the when; do
  not convert between windows.
- `imported-by` (Go) and `dependent repositories` (libraries.io SourceRank
  detail) are adoption analogs, not downloads — put them in the relevance
  line, keep `downloads` null.
- A package whose repo link 404s but whose name matches a live repo on the
  host: record the live repo as the candidate, note "repo link rot —
  resolved by name" (one permitted lookup), and keep the package field.
