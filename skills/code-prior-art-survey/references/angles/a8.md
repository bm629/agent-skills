# Angle a8 — model/AI hubs (conditional)

- **Trigger condition:** the scope has ML involvement — an ML capability, a
  model-backed feature, or ML techniques in the keyword map. When false,
  this angle spawns no work and the map's `sources.skipped` says so.
- **Mechanism:** searching AI-artifact hubs — models, datasets, and hosted
  demo apps — and resolving them to their source repositories. For ML
  scopes, hub artifacts ARE prior art: a hosted Space demonstrating the
  exact capability is a working reference implementation.
- **Applicable group types:** per the registry; broadly `capability`,
  `technique`, `domain`.
- **Sources (registry ids, tier order):** `huggingface`, `kaggle`,
  `replicate`, `ollama-library`.
- **last_verified:** 2026-07-17

## Unique coverage

Model-adjacent reference implementations: the fine-tuned model for the
scope's task, the dataset that trains it, and — the underrated one — Spaces/
notebooks that wire a whole pipeline end to end. These rarely surface on
code-host metadata search (their repos are hub-side, not GitHub-side).

## Hub-artifact → candidate mapping (this angle's special rule)

Candidates remain REPOSITORIES. Hub artifacts map as:

- Model/Space/notebook WITH a linked source repo → the repo is the
  candidate; the hub artifact goes in the relevance line ("HF Space
  demoing X, 40k runs").
- Hub-native artifact with NO external repo → the hub page itself is the
  candidate (`host: huggingface`, the hub URL as `repo`, canonical id like
  `huggingface__<org>__<name>`); its hub metrics (downloads, likes) fill
  the signals analogs (`downloads` = hub downloads, honest `as_of`).
- Datasets are recorded ONLY when the scope has a data capability —
  otherwise a one-line note ("relevant dataset exists: <name>") for the
  caller.

## Source craft

### huggingface (tier 1)

The dominant hub: models + datasets + Spaces, all task-tagged.

1. **Task-tag pass** — map the scope's ML capability to pipeline tags
   (`huggingface.co/models?pipeline_tag=<task>`): time-series-forecasting,
   reinforcement-learning, text-classification, etc. Walk the tag filtered
   by the domain terms; sort by downloads (Pass 1) AND by recently-updated
   with no download attention (the no-floor pass — new models have no
   downloads yet).
2. **Full-text pass** — `huggingface.co/search` per canonical + expansions
   across models/datasets/spaces (e.g. `trading`, `financial forecasting`).
3. **Spaces pass** — Spaces matching capability terms are end-to-end
   reference apps; open each hit's "Files" tab — the app source is right
   there (that IS the implementation; record the Space as candidate with
   its linked repo when one exists).
4. Worked example (capability "signal prediction" in a trading scope):
   - `models?pipeline_tag=time-series-forecasting` + search `stock
     prediction`, `trading signal` → 6 models (2 with GitHub repos → repo
     candidates; 4 hub-native → hub candidates);
   - `spaces search: trading strategy` → 3 Spaces (1 with a full backtest
     pipeline in its Files — strong candidate).
5. Extraction: hub downloads/likes + `as_of`; license from the model card
   (often missing — null, and note the gap; unlicensed models matter to
   the caller's legal review).
6. Model cards cite papers + training data — names found there go to notes
   as leads (a7's material, not yours).

### kaggle (tier 2)

1. **Datasets pass** per domain/capability term — only when a data
   capability is in scope (see the mapping rule).
2. **Notebooks pass** — `kaggle.com/code` search per capability term:
   high-vote notebooks implementing the scope's task are real
   implementations (canonical id `kaggle__<user>__<slug>`, votes in the
   relevance line). Competition-winner notebooks for a matching problem
   are exceptional prior art — check whether a competition matching the
   scope exists (`kaggle.com/competitions` search, one query).
3. Kaggle code skews experiment-grade — normal; relevance lines say
   "competition notebook, 400 votes; experiment-grade".

### replicate (tier 3)

1. `replicate.com/explore` search per capability term; every model card
   links its source (usually GitHub) — resolve to repo candidates.
2. Run-count = adoption analog (relevance line).
3. Coverage is generative-AI-skewed; zeros outside that space are normal.

### ollama-library (tier 3)

1. `ollama.com/library` + community search per capability term — matters
   when the scope wants LOCAL model deployment (check the scope context).
2. Library models are packaging of upstream weights — the upstream (on HF
   usually) is the real artifact; record the ollama packaging in the
   relevance line ("packaged for local use as ollama/<name>").
3. Zeros for non-LLM scopes are expected and recorded.

## Coverage duties

Cells per applicable (group × active a8 source), applicability being
exactly each source's `group_types` in the registry — check them, never
assume (capability groups owe all four sources; technique groups only
huggingface; domain groups huggingface + kaggle). Zero-hit cells with
query strings as always; hub searches record the tag/filter combination
used ("models?pipeline_tag=time-series-forecasting + 'trading'").

## Failure modes and fallbacks

- Hub search relevance is noisy for niche domains: combine the task-tag
  pass (precise but coarse) with full-text (broad but noisy); record both
  cells' queries — the combination is the method.
- Model cards without licenses or provenance: record with nulls + a note;
  never infer a license.
- Gated/private models (request-access walls): note "gated" in the
  relevance line; the existence is still a finding.
- The hub's trending/downloads API shifts: UI numbers suffice; `as_of`
  covers drift.

## Candidate quality hints

For ML scopes the strongest candidates here are Spaces/notebooks wiring the
FULL capability (data → model → output), not bare model weights — say which
kind each candidate is ("end-to-end Space" vs "weights only, no pipeline").
Weights-only hits still matter (they answer the scope's model-selection
question later) — one honest clause each.

## Worked end-to-end example

Scope: trading bot with an ML signal capability. Group
`kw-cap-signal-prediction` × a8:

1. huggingface: task-tag pass (time-series-forecasting, 2 sorts) + text
   pass (`trading signal`, `stock prediction`) + spaces pass → 9 artifacts
   → 4 repo-linked candidates, 3 hub-native candidates, 2 dataset notes.
2. kaggle: notebooks `trading signal prediction` (vote sort + recent sort)
   → 3 notebook candidates; competitions search → 1 matching competition
   → its top public notebook harvested.
3. replicate: `trading` → zero (recorded; generative-skew note).
4. ollama-library: zero (scope wants no local LLM; recorded with reason —
   arguably belongs in sources.skipped next map revision; noted).
5. Net: 11 candidates + 2 dataset notes + 1 map-improvement note; cells
   for all four sources.

## Task-tag mapping (scope capability → hub pipeline tags)

| Scope capability shape | HF pipeline tags to walk |
|---|---|
| forecasting/signals | time-series-forecasting |
| text understanding | text-classification, token-classification, zero-shot-classification |
| conversational/agent | text-generation, conversational |
| vision | image-classification, object-detection, image-segmentation |
| speech | automatic-speech-recognition, text-to-speech |
| embeddings/search | sentence-similarity, feature-extraction |
| RL/decision | reinforcement-learning |

Map every ML capability in scope to 1-3 tags; each mapped tag gets the
two-sort walk (downloads + recent). Unmappable capabilities fall back to
full-text search only — note the mapping gap.

## License-risk capture (matters more here than anywhere)

Model licenses are chaotic: custom "community licenses" with use
restrictions, research-only clauses, no license at all. Per candidate:

- Record the license string the card states, verbatim (`signals.license`);
  null + a note when absent.
- Restriction classes worth one clause in the relevance line:
  research-only, no-commercial, output-ownership claims, use-case bans.
- Never summarize a custom license as "open source" — name it and let the
  caller's legal review judge.

## Dataset-capability rule (worked)

Scope WITH a data capability ("market-data ingest"): dataset hits become
candidates (canonical id, hub URL, size/downloads in signals-analogs).
Scope WITHOUT one: the same hit is one line in notes ("relevant dataset:
<name>, <size> — no data capability in scope"). The caller's scope authority decides
which, never the scout's enthusiasm.

## Weights-vs-pipeline decision table

| Artifact form | Candidate? | Relevance framing |
|---|---|---|
| Space/notebook with full pipeline | yes — strongest | "end-to-end reference app" |
| model + linked training/inference repo | yes | "weights + code" |
| weights only, documented card | yes | "weights only — model-selection input" |
| weights only, bare card | yes, low | "undocumented weights" |
| dataset | per the data-capability rule | — |

## Hub-native id and signal conventions (recap for this angle)

- Hub-native candidates: `id: huggingface__<org>__<name>` /
  `kaggle__<user>__<slug>`; `repo` = the hub URL; `host` = the hub id.
- `signals.downloads` = the hub's download number (it IS a download count —
  the one registry-style metric hubs report natively); likes/votes/runs go
  in the relevance line by name.
- `package` stays null for hub artifacts (no package registry involved)
  unless the model also ships as a pip package (then both are recorded).
- Model-card citations (papers, base models) are notes-leads: base-model
  lineage ("fine-tune of <base>") is one relevance clause — it is this
  angle's fork-honesty analog: a thin fine-tune of a famous base is not an
  independent finding, and saying so keeps convergence honest.
