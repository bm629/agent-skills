# Angle a2 — weakness-to-attack-pattern traversal

**Precondition:** always.

**Mechanism.** Taxonomy traversal along the published mapping chain: weakness classes to attack
patterns to adversary techniques, walkable in either direction. Entered from the product's
surfaces, it yields attack patterns with their prerequisites and mitigations; entered from a
specific vulnerability, it generalises that vulnerability to a reusable pattern.

**Sources:** `cwe`, `capec`, `attack`.

**Applicable group types:** `weakness`, `attack-pattern`.

**Cap:** 50 attack-pattern entries. **Ordering signal:** the attack-pattern catalog's own
Likelihood Of Attack field.

## Query strategy

1. For each `weakness` group, resolve its canonical term to weakness identifiers. Where the map
   already carries identifiers, use them; where it carries prose, search the weakness catalog
   for the concept and take the entries whose description matches, applying the group's negative
   terms.
2. From each weakness identifier, follow the published mapping to attack patterns. This is the
   traversal — do not search the attack-pattern catalog independently for the same concept, or
   you will surface entries the mapping deliberately excludes.
3. From each attack pattern, follow the mapping to adversary techniques where one exists, and
   record those as `attack-technique` candidates.
4. For each `attack-pattern` group, traverse the other direction: from the pattern to the
   weaknesses it exploits, which enriches the weakness groups' relevance lines.
5. Record the traversal path in each candidate's relevance line — "reached from CWE-639 via the
   published mapping" is a grounded relevance; "relates to authorization" is not.

## Unique coverage

Attack patterns carry prerequisites, required attacker skill, and stated mitigations, none of
which a vulnerability record contains. This is also the only angle that can generalise: a
specific advisory found by another angle becomes a reusable pattern here, which is what makes
the survey's output durable rather than a list of this month's vulnerabilities.

## Failure modes specific to this angle

- **Independent search instead of traversal.** Searching the attack-pattern catalog directly for
  a concept returns entries the weakness mapping deliberately omits, and the resulting coverage
  claim is not reproducible from the map.
- **Stamping the wrong cadence.** The weakness catalog ships several releases a year while the
  attack-pattern catalog can sit unchanged for years. Record each release separately; one
  `as_of` for both is wrong.
- **Reading the technique knowledge base as a threat list for this product.** It describes
  adversary behaviour in general; only techniques reached through the mapping belong here.

## Sanitization

The weakness catalog offers a public API and a versioned corpus download; the attack-pattern
catalog is a corpus download. Both are fetched, so both pass through a
**content-sanitization guardrail** before use, recorded per source. An API returning structured
JSON is not thereby trustworthy input.

## Fallbacks

For the weakness catalog: the versioned corpus download if the API is unavailable, then a prior
pinned release. For the attack-pattern catalog: a prior pinned release. For the technique
knowledge base: the attack-pattern catalog's own technique cross-references, which is a
degraded but honest path — record it as `partial` with the cause.
