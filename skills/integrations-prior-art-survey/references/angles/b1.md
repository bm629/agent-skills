# `b1` — package-registry SDK adoption

## Mechanism

Walk the map's `service` group AND the package registries' own search surface — surfacing
services with a widely-used SDK and no connector. The package is resolved from the vendor's own
docs page, never by guessing a name.

**This angle takes its input from WAVE 0 or the capability map, never from another search child.**
It discovers from the vocabulary map's own groups and enriches from its own channel. The
cross-angle join happens at two places that are not angles — the coordinator's in-memory merge and
the extract child's deep read, both wave 2.

## Axes it searches

- **`service`** — third-party services already named in the scope
- **`category`** — the integration categories the product's capabilities imply

## Sources

## Cap and ordering

**Cap: `40`.** BUDGET, and it BINDS (B3, 2026-09-03). 59.2% of sampled Nango rows carry a vendor-confirmed,
PUBLISHED npm SDK, extrapolating to ~402 of the 680 rows with a concrete vendor host, and one
mid-sized category clears 40 on its own (crm, 88 x 59.2% ~ 52). The drop-if-under-40 condition
does not fire. **The RATE is the measurement**: the sample's size and membership were not recorded, so like a3's and b3's it is not re-derivable from what was written down. The corpus filter is a row with a CONCRETE VENDOR HOST — from authorization_url,
token_url or proxy.base_url, excluding ${connectionconfig.*} templates — NOT "rows carrying
docs", which matches 990 of 990 and points at nango.dev rather than the vendor.

**Ordering: the map's own GROUP DECLARATION ORDER -- the position of the group that PRODUCED the row, total over both axes this angle walks (service AND category) -- then the package name ascending. The adoption signal is recorded in notes[], not used as the drop order: only ecosystems-packages yields dependent counts, and npm-downloads and pypistats return download counts for ONE named package per request.** Transcribe it VERBATIM into `bound.ordering`. Where the run
could not apply it, record the ordering it DID apply and say why in `ordering_deviation` — an
ordering nobody can re-apply is a cap with no honesty behind it.

## Precondition, in BOTH directions

**It holds when:** `integrations.complexity = complex OR archetype.primary in {library-sdk, cli-tool, api-service}`.

**It does NOT hold when** none of those disjuncts is satisfied; the map records `holds: false` naming the DECIDING value, and this angle is not dispatched.

## What this angle uniquely covers

services whose adoption shows up as SDK pulls rather than as a connector listing.

## No sibling dependency

This angle names no other angle's output anywhere above. Its mechanism reads the vocabulary map and
its own sources, so a survey missing any other angle still dispatches this one. Where a naive
reading of the taxonomy would have it consume `a1`'s candidates, the resolution is that it
DISCOVERS from wave 0 and ENRICHES from its own channel.

## Absent input

If every source above is unreachable, record each cell with its status and observable cause, set
`outcome: vacated` with the cause, and record NO candidates — recording one would mean a search
happened. If the angle was ruled out by the map, `outcome: not_run` with the map's verdict, and
nothing else.
