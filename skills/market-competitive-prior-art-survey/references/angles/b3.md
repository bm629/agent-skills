# Angle b3 — package-ecosystem adoption retrieval

**Precondition:** `archetype.primary in {library-sdk, cli-tool}` OR
`business.model = open-source`.

**Mechanism.** Pull download and adoption time series for competing packages from the
registries that publish them.

**Sources:** `npm-downloads`, `pypistats`, `homebrew-analytics`, `ecosystems-packages`.

**Applicable group types:** `category`, `seed-product`.

**Cap:** 30 candidates — declared in `references/source-registry.yaml`, which is the single source. **Ordering signal:** download volume over the most recent complete period, then trend direction.

## Query strategy

1. Resolve each competing package to its registry coordinates. The canonical id is a **purl**
   (`pkg:npm/<name>`, `pkg:pypi/<name>`), which is an externally-owned standard — do not invent
   an id shape.
2. **npm** — `https://api.npmjs.org/downloads/point/{period}/{package}`. No auth. Returns the
   package name, a downloads count, and the start and end dates of the window.
3. **PyPI** — `https://pypistats.org/api/`. No auth. 180-day retention, known mirrors excluded,
   application-wide IP rate limiting; throttle and record a rate-limited cell rather than
   retrying hard.
4. **Homebrew** — `https://formulae.brew.sh/api/analytics/{category}/{days}.json` with category
   in `{install, install-on-request, build-error}` and days in `{30d, 90d, 365d}`.
   `install-on-request` is the more meaningful signal for a CLI tool: plain `install` counts
   dependency pulls, which measures other packages' popularity rather than this one's.
5. **ecosyste.ms** spans many registries through one API — 5,000 req/hr anonymous, 15,000
   "polite" if you supply contact information in the User-Agent or a `mailto` parameter. Be
   polite; it costs nothing and triples the budget.
6. Always record the WINDOW alongside a number. A download count with no period is unusable.

## Unique coverage

The only angle producing a defensible quantitative answer to "how much is this actually used".
Every other adoption signal in the survey is either a proxy (stars, ratings) or an assertion
(a vendor's customer count). Registry downloads are directly measured, published by the
registry itself, and comparable across time for the same package.

## Failure modes specific to this angle

- **Comparing raw counts across ecosystems.** npm's volume dwarfs PyPI's for structural
  reasons that have nothing to do with the packages. Compare within an ecosystem; across
  ecosystems, compare trend and rank, never absolute counts.
- **Reading `install` where `install-on-request` is meant.** See step 4.
- **Treating downloads as users.** CI pipelines dominate download counts for many packages.
  It is an adoption PROXY; record it as one, and never write "N users".
- **Ignoring mirror exclusion.** PyPI's stats exclude known mirrors, and other registries may
  not; a cross-registry comparison inherits that inconsistency.
- **Missing a package that is vendored rather than installed.** Some competitors ship as a
  copy-paste snippet or a template. Their download count is legitimately near zero, and that
  is a fact about distribution, not about adoption.

## Sanitization

Registry APIs return structured data, which is lower risk than a rendered page but not inert —
package descriptions and README content are author-supplied. Pass fetched content through a
content-sanitization guardrail and record the result per cell. Structured format is not
evidence that contents are safe.

## Fallbacks

`ecosystems-packages` — one public API spanning many registries, so a single registry's outage
does not empty the angle. Record the substitution in `retrieval_summary.degraded_sources` with
`fallback_used`.
