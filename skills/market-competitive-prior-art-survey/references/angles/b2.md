# Angle b2 — app-store / marketplace listing retrieval

**Precondition:** `archetype.primary in {mobile-app, game, browser-extension}` OR
`archetype.secondary` contains one of them.

**Mechanism.** Retrieve store listings for competing products: title, publisher, rating,
rating count, price, release and update dates, and category placement.

**Sources:** `itunes-search`, `steam-appdetails`, `chrome-web-store`.

**Applicable group types:** `category`, `seed-product`.

**Cap:** 20 candidates — declared in `references/source-registry.yaml`, which is the single source. **Ordering signal:** rating count, then recency of last update.

## Query strategy

All three sources were verified key-less by direct fetch on 2026-08-04. Their exact shapes:

1. **iTunes Search** — `https://itunes.apple.com/search?term=<q>&entity=software&limit=<n>`.
   Returns `resultCount` + `results`. Each result carries `trackName`, `trackId`, `sellerName`,
   `averageUserRating`, `userRatingCount`, `price`, `formattedPrice`, `version`, `releaseDate`,
   `currentVersionReleaseDate`, `genres`, `bundleId`. Reported ~20 calls/min — throttle, and
   record a rate-limited cell rather than hammering it.
   The canonical id for a result is `APPLE-<trackId>`.

2. **Steam** — `https://store.steampowered.com/api/appdetails?appids=<id>`. Returns an object
   keyed by the app id string, with `success` and a `data` object carrying `name`, `type`,
   `is_free`, `developers`, `publishers`, `price_overview`, `platforms`, `metacritic`,
   `categories`, `genres`, `recommendations`, `release_date`.
   **`price_overview` is ABSENT on a free title** (`is_free: true`). Read the absence as "free",
   never as a price of zero, and never as missing data.
   The canonical id is `STEAM-<appid>`. Only this endpoint is used; other Steamworks Web API
   methods require a key and are out of scope.

3. **Chrome Web Store** — the official API was **retired**. Public HTML pages only. Extract
   conservatively and record what the page actually showed.

Query each source only for the archetypes it covers: do not look for a browser extension on
Steam or a game on the Chrome Web Store. A cell for an inapplicable (group x source) pair
should not exist rather than be recorded as an empty search.

## Unique coverage

Install-base and rating signals for distribution channels that have little or no web presence.
A mobile-first competitor may have no meaningful marketing site at all, and would be invisible
to a1 and thin in a2, while carrying a hundred thousand ratings in a store.

## Failure modes specific to this angle

- **Inferring a price of zero from an absent `price_overview`.** Verified: free titles simply
  omit the field. This is the single most likely silent error in this angle.
- **Comparing ratings across stores.** A 4.5 on one store and a 4.5 on another are computed
  from different populations under different review policies. Record each with its store and
  its count; never average them.
- **Assuming an app id.** Resolve ids by search; a guessed numeric id returns a real listing
  for the wrong product, exactly as it does on Capterra.
- **Treating store rank as market share.** Rank is category- and region-specific and changes
  daily. If you record it, record the category, the region and the date, or do not record it.

## Sanitization

Store listing text is publisher-supplied marketing copy, and review excerpts are user-supplied.
Pass fetched content through a content-sanitization guardrail and record the result per cell.
A listing's description is a claim by its publisher, not a fact — attribute it as such.

## Fallbacks

`chrome-web-store`. Both API-backed stores were verified key-less, so the realistic failure is
one store being unreachable rather than all three; the Chrome Web Store has no API at all and
is read as public HTML, so it shares no infrastructure with the other two and cannot fail with
them. Record the substitution in `retrieval_summary.degraded_sources` with `fallback_used`.
